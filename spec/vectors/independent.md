# Independent test vectors

`v1.json` is generated by this repository's library, the same library its server and conformance suite import,
so a mistake in that library would be in the vectors, the server and the suite alike
([protocol.md](../protocol.md) section 15 says so). `independent.json` is the small set that does not depend on
it: every byte in it comes from an RFC, from a standard digest example, from OpenSSL or Python's standard
library, or was written out by hand from the text of protocol.md. `v1.json` is not rewritten or replaced.

## What is in it

| Section | What | Where the bytes come from |
| --- | --- | --- |
| `sha256` | The digests of the empty string, `abc`, the 448-bit message and one million `a` | NIST FIPS 180-4 examples; the digests are recomputed with Python's `hashlib` |
| `ed25519` | Five key pairs, messages and signatures: tests 1, 2, 3, 1024 and SHA(abc) | RFC 8032 section 7.1, parsed from the RFC's text; each is checked with `cryptography` (OpenSSL): the public key from the secret, the signature from the message, and the verification |
| `base64url` | Encodings and the spellings that are not the one canonical spelling | RFC 4648 section 10's seven vectors, unpadded in the URL alphabet; `fb ff` and `fb ef be` for the characters the alphabets differ in; the refused spellings follow RFC 4648 section 3.5 and protocol.md section 2.5 |
| `canonical` | Canonical JSON | RFC 8785 section 3.2.3's sorting test data, parsed from the RFC, its keys written as protocol.md 5.1 says; and two cases written by hand: every escape and every character written raw, and nesting with sorted keys |
| `messages` | Two signed messages | The canonical bytes are written by hand. The id is `hashlib`'s SHA-256 of them; the signature is OpenSSL's Ed25519 over `SIMON-MESSAGE\n` and them, with the RFC 8032 TEST 1 secret key (protocol.md section 1) |
| `requests` | Two request signing strings, one with a body | The eight lines are built by hand (protocol.md section 8); the body hash is `hashlib`'s; the signature is OpenSSL's, with the same key |

## How they were derived

```sh
curl -sLO https://www.rfc-editor.org/rfc/rfc8032.txt
curl -sLO https://www.rfc-editor.org/rfc/rfc8785.txt
python3 -I spec/vectors/derive-independent.py rfc8032.txt rfc8785.txt > spec/vectors/independent.json
```

`derive-independent.py` imports nothing from this repository and reads no other file in it. It needs Python 3
and the `cryptography` package. Ed25519 is deterministic, so the output is the same every time, and the script
asserts its own inputs on the way: every RFC 8032 public key follows from its secret key, every signature
follows from its message and verifies, and every hand-written canonical text parses to the object it stands for.

## How they are used

- `test/spec/independent.test.ts` checks the file against itself with Node's crypto alone. It imports nothing
  from the library, so it fails when the file is wrong.
- `protocol/test/independent.test.ts` checks the library against the file: key tokens, signatures, ids, canonical
  text, base64url and signing strings.
- An implementation in another language reproduces the file the way it reproduces `v1.json`.

## What they are not

They are not an independent implementation of SIMON. They show that the library agrees with RFC 8032, with
OpenSSL, with `hashlib` and with a hand reading of sections 1, 5.1 and 8 on these bytes. They do not cover
resolution, documents, envelopes, claims or any rule that only this protocol has, and the Python client, which
reproduces `v1.json`, was written beside the library by the same authors. Version 1 stays unstable until two
independent implementations interoperate (protocol.md, Status).
